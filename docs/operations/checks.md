# Checks

What verifies a change, locally and in CI, and the time each may take.

## Locally

`tools/check.sh` runs the checks in three tiers; each includes the one before it. Its builds are the CI cells' presets from `CMakePresets.json`.

| Tier | Runs | Budget |
|---|---|---|
| `changed` | The source, module, length, API documentation and snippet rules, the Unicode files against their SHA-256, test hygiene, the organization's documentation check, `clang-format` on the changed C files, and the `linux-clang-20-asan` preset (assertions on) with the CTest labels the changed files reach. | under 2 minutes |
| `pr` | Every rule on every file, the generated tables against the generator and their ceilings, clang-tidy, the `linux-harfbuzz` and `linux-clang-20-asan` presets, and 10 seconds of fuzzing per target. | under 10 minutes |
| `full` | Also every other Linux preset (ThreadSanitizer, the shared library with the HarfBuzz functions, the package test and the exports test, every optional component left out, 32-bit x86, Clang and GCC Release) and 60 seconds per fuzz target with the ICU comparison. | under 20 minutes |

Run `changed` before every push. On the shared development machine, run `pr` and `full` through the workspace's heavy-job wrapper. Builds go to `out/<preset>` and the other trees to `out/check-*`, each with its log beside it.

## In CI

`.github/workflows/ci.yml` runs on every pull request, on every push to `main` and every night. The Linux jobs run in the organization's CI image, pinned by digest, and install nothing. The ruleset requires only its `required` job, which passes when every other job passed or was skipped, and the title check.

| Job | What it guards |
|---|---|
| `changes` | Whether a pull request changes anything beyond documentation; when it does not, the build jobs below are skipped. |
| `docs` | The organization's documentation check, run by its `docs-check` action from the pinned commit of `.github`, so a rule reaches this repository when the pin moves: allowed files, the em dash, record numbers, page sizes, links. `tools/ucd/` is excluded. |
| `zizmor` | The workflows: injection, persisted credentials, permissions, unpinned actions. |
| `checks` | `clang-format`, the family's source rules, the module graph, lengths, API documentation, documentation snippets, that every file in `tools/ucd/` matches its SHA-256 in `tools/ucd/README.md` (`tools/check_ucd.py`), test hygiene and that every test carries a label in the HarfBuzz and shared configurations (`tools/check_test_hygiene.py`), that the documentation site builds, that `munigen` regenerates `src/generated/` byte for byte, the table ceilings, and clang-tidy. It runs on documentation changes too. |
| `build` | One call of the organization's `cpp.yml` per preset: GCC 14 and Clang 20 in Release, Clang with AddressSanitizer and UBSan (each test repeated up to three times on a pull request, so a flaky one fails before it merges), Clang with ThreadSanitizer, the shared library (with the HarfBuzz functions, so they link only against what it exports), the static library with the HarfBuzz functions, every optional component left out, 32-bit x86 (GCC 14 with `-m32`, where `size_t` and pointers are 4 bytes and `uint64_t` is 4-byte aligned in structs), macOS and `clang-cl` on Windows. All build with warnings as errors; the shared and HarfBuzz cells run the package test, and the shared cell checks that the library exports the public functions and nothing else. ccache is restored on every run and saved only from `main`. |
| `msvc-headers` | Every public header compiled by MSVC's `cl` as C17 and C++17 with `/W4 /WX`. |
| `fuzz` | Every fuzz target from its seeds in `test/seeds/`, four at a time, through `tools/fuzz_target.sh`: 20 seconds each on a pull request, from the seeds alone, and 90 seconds on `main` and 600 at night, from the cached corpus too. Dispatching `ci` by hand runs the night's fuzzing, 600 seconds per target unless its `fuzz-seconds` input, a whole number from 1 to 800, says otherwise; past 800 the three waves of four targets would leave the 50-minute timeout no time to minimize and save the corpus. On `main` and at night each corpus is then minimized and saved. An input that runs past 30 seconds is a finding too. A finding prints only the target, the kind of each finding and the sanitizers' report; its input, its seed, the logs and the corpus stay on the runner and are never uploaded, and a run that found something saves no corpus. |
| `quarantine` | The quarantined tests ([Quarantine](#quarantine)) of the `linux-clang-20-asan` preset through the family's `tools/run_quarantine.sh`, with the test presets' timeout and jobs, at night and on a manual run. |
| `web` | The library and its tests under Emscripten and Node, but the quarantined ones, and the size of the static library in total and per optional component. The image has no Emscripten, so this job uses the runner and the emsdk action. |

`pr-title.yml` checks that the pull request title is a conventional commit with a scope from `AGENTS.md`, and `pr-gate.yml` closes a pull request from outside the organization unless it closes an issue labeled `accepted`. `codeql.yml` runs CodeQL on every pull request and on `main`, building with GCC 14 (an advanced setup, since the default one builds with the runner's GCC 13). `scorecard.yml` grades the repository's security practices weekly for the README badge, and Dependabot proposes updates of the pinned actions once a week in one pull request.

## Tests

Each suite in `test/` is one executable, registered with CTest under its name and labeled with it. The data suites read the Unicode files in `tools/ucd/`. The white-box suites (properties, identifier, case, security, writer) are not built in shared builds. All but writer include `src/tables.h` for the generator's hashes; writer starts the output writer near `SIZE_MAX`, which no real input can reach in a test. No test reports itself skipped; a test preset that finds no test fails, and so does a CI cell where a test is skipped or not run. `tools/check_test_hygiene.py` rejects sleeps, wall-clock reads, retry loops and skips in the test sources and skip properties in the CMake files; a use that must stay carries `// hygiene: <reason>`, in a comment and with a reason of at least three words, on its line or the one before. It also rejects a test registered without a label, in every build `tools/check.sh` configures; `--self-test` runs it over the fixtures in `tools/test_hygiene/`. `test_guide.c` and `test_guide_harfbuzz.c` run the C snippets of `docs/user/` as written; `tools/check_guide.py` fails when a snippet and its copy differ. `test_results.c` hashes what normalization, NFKC_Casefold, case conversion and skeletons give, and the identifier, restriction level, mixed number and resolved script verdicts, for every code point, the sequences of `NormalizationTest.txt` and a few strings that depend on context, and fails when the hash is not the one recorded for `MUNI_RESULTS_VERSION`. The `changed` tier runs `tools/check_results_history.py` against the base, which fails when the diff removes or edits a recorded version; its `--self-test` runs it over the fixtures in `tools/results_history/`.

## Quarantine

A test that fails without a fault in the change under test is quarantined, as [maul-conventions.md](../internals/maul-conventions.md) says: an issue records the failure and its run, and the test takes the `quarantine` label through `maul_add_test(... QUARANTINE)`, or `maul_quarantine(<test>)` for a test registered another way. Every test preset leaves the label out (`CMakePresets.json`), and so does the `web` job's test step, so neither the pull request cells nor `tools/check.sh` run a quarantined test. The `quarantine` job runs them every night, and the `web` job's quarantine step runs them under node the same night, with the same 300-second limit per test and a WebAssembly memory trap in place of a sanitizer report: a failure or a timeout is a warning and a line in the job summary, and a test that is skipped or not run, a sanitizer report or a crash fails the job. A test leaves quarantine when its issue's fix lands and the nightly has passed it 14 nights in a row. No test is quarantined now.

## Fuzzing

Every fuzz target (`test/fuzz_<area>.c`) checks properties that must hold for any input rather than known answers: no crash, no broken assertion, piecewise iteration giving the whole-text answer, round trips, idempotence where the standard promises it, agreement between parts (validation and conversion, normalization and its quick check, NFKC_Casefold and the normal forms), and output through a short buffer matching output through a large one. `fuzz_icu` compares with ICU, a test-only oracle, where both Unicode versions agree; its header lists what it leaves out and why. The targets take at most 256 bytes, but `fuzz_bidi_long` repeats its input into a text of 2 KiB to 128 KiB, so work that grows faster than the text runs past libFuzzer's 30-second timeout and is a finding.

Each target's corpus carries over from run to run in one Actions cache entry, `fuzz-corpus-<run id>`, holding a directory per target. Runs on `main` and at night restore the latest entry and add the committed seeds, which are the floor. After fuzzing they minimize each target's corpus through `tools/fuzz_target.sh --merge` into a fresh directory, swap it in only when the merge finished, and save a new entry. A clean merge prints one line, the target and the size of its merged corpus; an input that crashes the target during the merge fails the step and prints the same report as a fuzzing finding, the target, the kind of finding and the sanitizers' report, never the input. A run whose fuzzing or merge found something saves nothing. A pull request, or a dispatch on any other branch, fuzzes from the seeds alone and neither restores nor saves, so no branch but `main` reads or writes the corpus. A target whose minimized corpus passes 25 MB fails the step, and the corpora are not saved, so one target cannot crowd the others out of the cache. The organization's other libraries run one fuzz job per target, each with its own cache. This repository has ten targets in one job, four at a time, because ten more containers per run would cost more runner time than the targets' corpora need, and the corpora are still kept and minimized separately.

A crash a fuzzer finds becomes a test in the suite of its module (see [development.md](development.md#reproducing-a-fuzz-finding)).

## Budgets

Over a budget, tests are pruned or merged before anything else is added. The pull request check takes about two minutes and the run on `main` about five, most of it the fuzz job. The night run fuzzes each target for 600 seconds, about 30 minutes in all: it is the standard's extended nightly run, which may take up to two hours and is not a required check; a build cell takes under a minute and a half, with or without ccache.
